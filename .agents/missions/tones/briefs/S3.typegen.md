Goal: teach typegen the new `tones` token category so colour style props type-accept `<colourToken>/<toneName>` (e.g. `'blue.500/medium'`).

Background: "tones" are a new token category declared through `tokens()`, e.g.
`tones: { medium: { surface: { value: '10%' }, line: { value: '34%' } }, hush: { value: '6%' } }`.
In the lowered BaseSystem these become entries with category `tones` and keys
`tones.medium.surface`, `tones.medium.line`, `tones.hush`. The tone NAMES are
the first path segment after the category: `medium`, `hush`. The atomic
compiler (not your job) will resolve `bg="blue.500/medium"`.

Scope (only these):
- `packages/reference-rs/modules/typegen/src/emit/tokens.rs`
- `packages/reference-rs/modules/typegen/src/emit/style.rs`
- `packages/reference-rs/modules/typegen/src/emit/strict.rs`
- `packages/reference-rs/modules/typegen/src/diagnostics/collect.rs` only if needed
- typegen tests: `packages/reference-rs/modules/typegen/src/tests/*.rs`, `packages/reference-rs/modules/typegen/tests/**` (goldens + vitest tsc consumers)
- `packages/reference-rs/modules/typegen/SPEC.md` and `README.md` (document the new stations / behaviour)

Required behaviour:
1. `tones` is a known token category: a system with tones must NOT produce the
   `TGN-W-UNKNOWN-TOKEN-CATEGORY` diagnostic for it (`is_known_token_category`).
2. Emit `export type ToneToken = 'firm' | 'ghost' | 'medium' | 'strong';` — the
   sorted, de-duplicated FIRST path segments of every `tones` entry (strip the
   `tones.` prefix, take up to the first `.`). Do this with a dedicated grouping
   function, not a `CATEGORIES` row (a row would emit `'medium.surface'`). When
   the system has no tones, print `export type ToneToken = never;` (always emit
   it whenever the token unions are emitted at all, like the core categories
   colors/spacing/radii).
3. Directly after it emit
   `export type TonedColorToken = \`${ColorToken}/${ToneToken}\`;` (always, same
   condition as ToneToken).
4. The `Tokens` interface gains `tones: ToneToken;` (always present, like the core categories).
5. Colour props: `COLOR_VALUE` in style.rs becomes
   `StylePropValue<ColorToken | TonedColorToken | (string & {})>`.
6. Strict colour props (`COLOR_VALUE_PARTS` in strict.rs) add `"TonedColorToken"`
   right after `"ColorToken"`. Do NOT add `tones` to `KNOWN_STRICT_CATEGORIES`.
7. Tests (Rust, in src/tests): add stations named `TYP-TONE-01..` covering:
   ToneToken from nested per-role leaves plus a flat leaf (first-segment dedupe);
   `never` when no tones; TonedColorToken alias printed; no unknown-category
   diagnostic for `tones`; open colour prop includes TonedColorToken; strict
   colour parts include TonedColorToken.
8. A vitest tsc consumer (follow the existing pattern in `tests/strict.test.ts` /
   `tests/tsc.ts`): with a system that declares a colour and tones, under strict
   emit `{ bg: 'blue.500/medium' }` typechecks and `{ bg: 'blue.500/mediun' }`
   is a type error; under open emit both typecheck (string hatch).
9. Update the committed goldens via the CLI only:
   `TYPEGEN_UPDATE_GOLDENS=1 pnpm agentrs c typegen`. Every golden diff must be
   explained by items 2–6 only (new aliases, the Tokens field, the colour value
   union); nothing else may move.

Constraints: no new dependencies. Do not touch atomic, base-system, canon, lib,
neo, or docs. No `#[allow(...)]`, no clippy suppressions; follow the file-header
and quality rules in AGENTS.md section 4. Keep functions small.
