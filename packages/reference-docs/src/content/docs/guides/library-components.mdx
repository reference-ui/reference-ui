# Library components

Older component libraries saved keystrokes with monolithic components,
favouring convenience over composition. Once your product needed something they
didn't plan for, every change was a workaround.

`@reference-ui/lib` favours patterns over widgets: a small set of transparent
components that humans and agents can both understand.

## What's in the library

A component joins the library only when the browser has no native equivalent,
the behaviour is hard to rebuild (focus trapping, date math, positioning) and
many products need the same API. Each one falls into one of three kinds.

## What's not in the library

The library leaves out components with no hard behaviour, and components
that mean something different in every product, such as a card or a navbar.

You build them from [primitives](/primitives). A checkbox is an `Input` with
`type="checkbox"`, and [`Field`](/field) wraps a plain `Input` to give it a
bezel.

A new pattern name is not a reason for a component either.

## Patterns are compositions

Dialogs, drawers and selects are not separate components. Each is a
documented composition of the components above. A dialog is an `Overlay`
with `role="dialog"`:

```tsx
<Overlay open={open} onOpenChange={setOpen}>
  <Overlay.Trigger>Delete project</Overlay.Trigger>
  <Overlay.Backdrop />
  <Overlay.Content role="dialog" aria-modal="true" aria-labelledby="delete-title">
    <H2 id="delete-title">Delete project?</H2>
    <Button onClick={() => setOpen(false)}>Cancel</Button>
  </Overlay.Content>
</Overlay>
```

| Pattern | Built from |
| --- | --- |
| Dialog, Alert Dialog | `Overlay` with a dialog role |
| Drawer, Sheet | `Overlay` with `edge` |
| Select, Autocomplete | `Combobox` with a `Listbox` popup |

## Stability

A small set is one we can keep stable. Patterns may change over time, but the
components underneath them are built to last.

**We are committed to never shipping a version 2.**
