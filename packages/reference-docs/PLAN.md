# Docs plan

The docs describe what Reference UI is, simply. The authoring surface is
small (style props, primitives, tokens, CSS); the machinery behind it is
complex and stays mostly out of view. Every page is written with the
`technical-writing` skill: one reader goal, one document type, no invented
behaviour (gaps are `TODO`).

## System vs Foundations

- **System** documents the core APIs (Neo, `reference-neo`): how to
  define tokens, fonts, animation, global CSS, style props and so on. It
  never says anything "ships" or is available by default; the core ships no
  flavour. Examples define their own values.
- **Foundations** documents what `@reference-ui/lib` ships: its actual
  colour palette, color modes, typography scale and fonts, and its tokens.
  It links back to the System page that explains the API it was built with.

## Open questions for the owner (first draft, 2026-10-17)

1. Atlas is drawn as a `ref sync` output, but sync emits only the
   `system`, `styled`, `react` and `types` packages; Atlas runs in the MCP
   server. Keep it in the diagram, or show Stylesheet + Types only?
2. `ref` ships in `@reference-ui/neo`, which is private and unpublished:
   what is its public name and version for the install commands?
3. One consumer import path: `@reference-ui/react` (generated by sync) or
   `@reference-ui/lib/primitives` (lib README)?
4. Style props on lib components don't paint values lib itself never uses
   (unbacked class + "no compiled class" warning) even with
   `extends: [baseSystem]`. Component demos use `className={css(...)}`
   meanwhile. Lib/Neo bug or wrong README advice?
5. Lib's `text.*` color group: keep or retire? (unused by components; dark
   `text.accent` darker than light)
6. Breakpoints are fixed in the engine; should users be able to change them?
7. Root README quick start imports `lib/styles.css` after `ref sync`; a
   synced project should import `@reference-ui/react/styles.css`.
